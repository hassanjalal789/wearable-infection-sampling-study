# Method traceability review

*Publication-stage review, carried out on 25 September 2026 for research I designed and conducted. It checks each executed rule against the document that set it and the published code that carried it out, and lists every place where they differ. It is new writing, prepared with AI assistance as the [contribution statement](CONTRIBUTIONS.md) records; each finding below was checked against the cited lines. The review changes no rule, code or result, and it was done without looking at any outcome beyond those already published.*

## How to read this

The [methods guide](METHODS_GUIDE.md) states the rules and the amendment that set each one. This review goes one step further: it names the function or constant that implements each rule, with line numbers in the published file, and the tests that exercise it. Where a value is recorded in the corrected run's [manifest](../results/primary_e3_run_83cc8d1/run_manifest.json), the manifest was compared as well. "Matches" means the code does what the governing document says; it does not mean the rule was a good choice.

## 2. Findings

### Planned rules or reporting items that the executed code did not carry out

- **F1. Daylight-saving transition days were not excluded.** The baseline protocol, [v1.1 §6.12](prereg-v1.1.md), says such days are "Excluded from all analyses. Counted and reported." No amendment removes the rule, and no published code implements it; the edge-case test for §6.12 only checks that an excluded day can be represented. The source timestamps are local clock times whose calendar alignment could not be established (see the [data and cohort guide](DATA_AND_COHORT.md#6-overlap-between-the-two-releases)), so how many transition days the data contain, and whether excluding them would change any threshold or alert, cannot be assessed from the published files.
- **F2. The paired warning-time difference was not computed.** A1 defines a descriptive paired difference in warning days on the participants detected under both schedules, with a bootstrap interval over that subgroup. No published script computes it and no published output reports it. The confirmatory summary reports each schedule's own median warning among its detected participants instead.
- **F3. Same-day detection and the at-or-before statistic are not reported.** A1 requires an alert on the onset day to be tabulated separately and an at-or-before statistic over [onset − 21, onset] to be reported. The runner records both for each participant and schedule (`primary_e3_experiment.py`, 199–201 and 221–250), but that file is withheld, and no published script or table summarises them.
- **F4. Part of the v1.1 reporting set was not produced.** v1.1 §11.3–11.4 lists intervals and reporting items for every comparison. Produced: detection proportions, W, L and T, θ with its BCa interval, the win ratio, warning-time medians and interquartile ranges among detected participants, and N per comparison. Not produced in any published output: a Clopper–Pearson interval for W/(W + L), the paired detection-proportion difference with its interval and McNemar counts, intervals for the warning-time and detection estimates, the realised alert burden per schedule, invalid days per schedule by reason, and a warning-time distribution figure. The calibration routine does assert that each threshold keeps the calibration-window alert rate within budget.
- **F5. The coarse-calibration flag is computed but not kept.** A2.1(2) asks for each schedule's coarse-calibration count to be reported. `calibrate_tau` returns the flag (`tod_z.py`, 217), but the runner does not store it.
- **F6. The S5 fallback is not logged.** v1.1 §7.3 says that after 1,000 rejected random placements S5 falls back to the earliest non-overlapping placement "and record[s] the event". The fallback is implemented (`schedules.py`, 194–199) but not recorded.

### Rules implemented differently from a document's wording

- **F7. Exclusion windows in the runner use onset dates only.** The cohort code anchors each infection episode on its onset date, or its diagnosis date when there is no onset date (`build_cohort.py`, `episode_anchors`; A3.5). The runner keeps only rows with an onset date (`primary_e3_experiment.py`, 145), following A5.5's "episode onset". An episode known only by a diagnosis date is therefore not excluded from calibration in the runner, or in the rolling-recalibration and multiple-episode sensitivity analyses. Its effect cannot be measured from the published files.
- **F8. One-day difference at onset − 28.** Cohort availability counts days strictly before onset − 28 (`build_cohort.py`, 112; A2.1), while runner calibration includes onset − 28 (`primary_e3_experiment.py`, 170; A5.5). Each follows its own amendment.
- **F9. M1 availability.** v1.1 §7.4 required both matched schedules to yield at least five retained rest samples as well as N′ ≥ 2. The code checks N′ ≥ 2 only (`schedules.py`, 253). A1 replaced §7.1–7.5 in full without restating the condition. The 40% unavailability rule of A5.8 is applied per participant over event-window days (runner 602–611; reveal script 102–107), and it was not triggered.
- **F10. Cohort filter order.** A2.6 lists the device filter before infection status; the code applies infection status first. The final cohort is the same; only the order of steps in the flow table differs.
- **F11. Baseline values.** A baseline day contributes a value only if it still has five rest samples in the hours that pass the seven-observation filter (`tod_z.py`, 138–146). This is slightly stricter than A3.1's wording.
- **F12. Significance boundary.** The gate tests p < α, and the Holm step tests p ≤ α. It makes no difference here: p = 0.5034.
- **F13. Rolling recalibration.** The rolling-threshold sensitivity sets a threshold for a day only after 16 earlier negative days (`sensitivity_analysis.py`, 319–320), which A7 does not specify.
- **F14. Warning time counts from the alert day.** An alert is raised on the second day of a two-day run, so a run on onset − 22 and onset − 21 counts as a detection with 21 days' warning. This follows the alert definition and is stated here so that readers know it.

### Records and tests

- **F15. The participant-flow record predates a reporting patch.** [`participant_flow.json`](../results/participant_flow.json) carries the note written before the calibration-minimum reporting patch described in the [execution log](../evidence/historical_execution_log.md#92-calibration-minimum-reporting-patch); the current `calibration_resolution.py` writes longer fallback text. The chosen minimum of 28 days is the same.
- **F16. The sign-test equivalence check prints, it does not assert.** [`verify_test_equivalence.py`](../src/verify_test_equivalence.py) runs a Monte Carlo comparison and prints the differences; the largest difference recorded in v1.1 §11.2 is 3.8 × 10⁻⁴.
- **F17. Test gaps.** No test covers the pair rule's calibration-unavailable branch or a loss for the first schedule, the 15/16-day calibration-floor boundary, the three-day gap boundary, the reveal and quality-check scripts, the execution guard, the power constants, or the same-day endpoint. `test_energy_model.py` tests a floor-based burst solver, not the nearest-integer rule the audit uses.
- **F18. The sensitivity output folder is not write-once.** Unlike the primary runner, the sensitivity script writes into its folder without refusing to overwrite (`sensitivity_analysis.py`, 387).

## 3. What the findings change

No result is changed. The published results remain the archived output of the code that ran. F1 and F7 concern data handling that could in principle affect individual thresholds or alerts; their effect cannot be measured without the withheld participant-level inputs, and I have not re-run anything to find out. F2 to F6 are reporting items that were planned and not produced. The rest concern wording, records and tests. None was found by looking at outcomes, and none has been acted on by changing code or recomputing results. The [methods guide](METHODS_GUIDE.md) and [results and limitations](RESULTS_AND_LIMITATIONS.md) now point to these findings where they state the affected rules, and the [publication notes](PUBLICATION_NOTES.md#material-corrections) record the corrections to the methods guide.
